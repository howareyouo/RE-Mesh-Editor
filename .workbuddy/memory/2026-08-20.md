## RE-Mesh-Editor: mesh import speed optimizations (blender_re_mesh.py)

Traced `importREMeshFile` → `importLODGroup` → `importMesh`. Parse stage already
numpy-vectorized; the serial `importMesh` build was the bottleneck for 20MB+ files.
Applied optimizations to `modules/mesh/blender_re_mesh.py`:

- P0-1: `use_smooth` list `[True]*N` → `np.ones(..., bool)` (no giant Python list).
- P0-2: hide armature (`hide_viewport/render=True`) BEFORE mesh import loop instead
  of only at the end → avoids per-skinned-mesh depsgraph eval (biggest single win).
  Also guarded the end-of-import hide against `armatureObj is None`.
- P0-3: dropped redundant `meshData.update(calc_edges=True)` → plain `meshData.update()`.
- P1-4: normals passed as float32 ndarray (no `.tolist()`); `TypeError` fallback to list.
- P1-5: hide submeshes that live in to-be-hidden collections during build (less redraw).
- P2-6: weight grouping precision 4→3 decimals (×~10 fewer `vg.add` calls).
- P2-7: parallel numpy prep for import — new `_prepImportMeshArrays` (worker thread,
  GIL-free: normals normalize + UV/color remap via face-derived loop indices) and
  `_buildImportActions` (ordered main-thread build, preserves reused-mesh linking &
  per-(LOD,group) merge). `ThreadPoolExecutor` only for submeshes ≥
  `PARALLEL_IMPORT_THRESHOLD` (50k verts); any prep error falls back to serial path.
  Module-level flags: `USE_PARALLEL_IMPORT_PREP`, `PARALLEL_IMPORT_THRESHOLD`.

Verified with `py_compile` (SYNTAX_OK). NOT runtime-tested in Blender yet — needs a
real 20MB mesh import to confirm speedup + correct skinning/normals/UV.

## Optimizations (4th pass): same-material submesh merge (array-level)
Implemented as opt-in `MERGE_SAME_MATERIAL_SUBMESHES = False` in blender_re_mesh.py.
Why it's the real lever: collapses 17 Blender builds -> ~(# distinct materials) builds.
- `_makeSubMeshImportArgs(subMesh, ...)`: extracted the per-submesh importMesh(**kwargs)
  dict out of the inline loop (shared by both paths).
- `_mergeSubMeshesToImportArgs(subs, ...)`: concatenates same-material submeshes in
  numpy with correct face-index offsets (v_offset); preserves normals/UV/color/weights.
  Buckets keyed by (materialIndex, color?, uv?, uv2?, normal?) profile for uniformity.
  Skips MPLY relPos, blend shapes, extra/secondary weights, reused meshes.
- `_appendBuildAction(...)`: builds the 'build' action + dispatches parallel prep via a
  `[None]` executor holder (so the ThreadPoolExecutor survives across the loop).
- `importLODGroup`: computes LODNum once; when merge flag on & not MPLY, buckets
  submeshes per visconGroup and emits one merged build action per bucket (>=2 subs),
  else per-submesh; `subMesh=None` for merged builds.
- `_buildImportActions`: guarded `MPLYRoot`/relPos + `meshOffsetDict[...]` writes against
  `subMesh is None` (merged meshes aren't reuse sources).
Merge math validated standalone (verts concat, maxFaceIdx<verts, weights/indices
contiguous) and `py_compile` SYNTAX_OK. STILL NOT runtime-tested in Blender.
To verify: set `MERGE_SAME_MATERIAL_SUBMESHES = True`, re-run import, confirm both
"Parallel mesh prep: K of N" built-count drop AND the `importMesh phase totals` line;
expect fewer/larger meshes and a lower total. Depending on material count, the win
scales with (#submeshes / #materials).

## 5th pass runtime fix (Blender-alpha is STRICT on VertexGroup.add)

addons\RE-Mesh-Editor\` — same file as workspace (auto-synced, both verified

## 12th pass: normals_c is the real cost → revert to .tolist() for custom normals
After validate gate-off: construct 229ms, normals_prep 73ms, normals_c 575ms,
uv_color 289ms, weights 217ms, finalize 2ms (build 1388ms). validate was only
~60ms — the 575ms is normals_split_custom_set_from_vertices ITSELF.
KEY LESSON: Blender's normals_split_custom_set_from_vertices() iterates every
vertex through the Python sequence protocol in C. Passing a numpy (N,3) array
forces per-row PySequence_Fast + numpy-scalar PyFloat conversion ≈ 1μs/vertex
(575ms @ 460k). `.tolist()` gives pure Python floats which C reads directly
(~30ns) — tolist + fast C ≈ 250ms. The earlier "numpy-direct, no tolist"
optimization was a NET REGRESSION (575 vs ~250). Reverted to
`normalized_normals.tolist()` with a comment explaining why. Expected build
~1050ms. NOTE: same lesson may apply to ANY Blender API that iterates sequences
in C (not foreach_set!) — numpy-direct is only safe for foreach_set/foreach_get
which have optimized numpy buffer paths.
